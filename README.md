# Hikyu Bank

Hikyu Bank is a simulated personal finance web application built to explore responsive web design, REST APIs, backend-driven business logic, authentication workflows, and multitier software architecture.

The application combines an HTML, CSS, and JavaScript frontend with a Java Spring Boot REST backend. Version 3 follows a four-tier architecture that separates presentation, application logic, data access, and storage responsibilities.

> **Demo environment:** Hikyu uses 100% synthetic financial data. No real bank accounts, financial transactions, emails, SMS messages, or financial services are connected.

---

## Overview

Hikyu began as a browser-based personal finance prototype and has evolved into a modular client-server application.

The current version supports:

- Two-step authentication and simulated identity verification
- Checking, savings, and credit account views
- Searchable and filterable transaction history
- Account-opening workflows
- Server-side account eligibility rules
- Financial alert preferences
- Notification inbox management
- Rule-based spending insights
- REST-based communication between frontend and backend
- Responsive interfaces informed by Figma prototypes
- Modular backend services and repository abstractions

The goal of Version 3 was not simply to add more features, but to restructure the application so individual parts of the system can evolve more independently.

## Architecture

![Hikyu Bank Four-Tier Architecture](docs/architecture.png)

Hikyu Version 3 uses four logical tiers:

| Tier | Responsibility | Main Technologies |
| --- | --- | --- |
| **Presentation** | UI rendering, navigation, forms, responsive layouts and user interaction | HTML, CSS, JavaScript |
| **Application Logic** | Authentication, account rules, alerts, notifications and workflow orchestration | Java, Spring Boot |
| **Data Access** | Repository contracts, adapters and communication between services and storage | Java repositories and adapters |
| **Storage** | Synthetic account, transaction, user, alert and notification records | In-memory storage and JSON seed data |

The application currently runs as a single Spring Boot process for local development, but the internal boundaries are intentionally separated.

### Request flow

A typical request follows this path:

```text
Browser UI
    ↓
REST Controller
    ↓
Application Service
    ↓
Repository
    ↓
MemoryDatabase
```

Responses travel back through the same boundaries:

```text
MemoryDatabase
    ↓
Repository
    ↓
Application Service
    ↓
REST Controller
    ↓
JSON Response
    ↓
Browser UI
```

This structure allows future storage providers, external APIs, AI services, or frontend clients to be introduced without rewriting the entire application.

## Features

### Authentication

Hikyu includes a two-stage simulated authentication flow.

Users:

1. Enter their username and password
2. Choose SMS or email verification
3. Request a six-digit verification code
4. Enter the generated code
5. Enter a demo PIN when email verification is selected

Verification challenges are generated by the backend and include:

- Five-minute code expiration
- Resend delay
- Attempt limits
- Server-side session management
- One-time code consumption

No real SMS or email is sent.

---

### Account Overview

The account dashboard displays synthetic financial accounts including:

- Everyday checking
- Savings
- Credit card

Users can review balances and account details from one dashboard.

---

### Account Opening

The application includes a simulated account-opening workflow for:

- Checking
- Savings
- Credit
- Loan
- Investment

Checking and savings accounts are restricted to one open account of each type.

Importantly, these rules are enforced by the backend application layer rather than relying only on browser-side validation.

Credit, loan, and investment requests remain simulated pending applications.

---

### Transactions

The transaction interface supports:

- Account filtering
- Category filtering
- Merchant/category search
- Income and expense records
- Transaction categorization

Transaction records are retrieved through the backend API rather than stored as authoritative financial data in browser storage.

---

### Financial Alerts

Users can create and manage simulated financial alerts such as:

- Low balance alerts
- Large transaction alerts
- Payment reminders
- Savings goals
- Scheduled reminders

Supported delivery preferences include:

- Email
- SMS
- In-app
- Calendar

These preferences are stored by the application, but external delivery providers are not currently connected.

---

### Notification Inbox

The notification system supports:

- Test notifications
- Unread/read status
- Resolution state
- Reopening notifications
- Deleting notifications
- Marking all notifications as read

Alert rules and generated notifications are stored as separate domain objects.

---

### Hikyu Assistant

Hikyu includes a rule-based personal finance assistant that can answer questions using the synthetic transaction dataset.

Example questions include:

- "Where am I spending the most?"
- "Review my subscriptions"
- "How much can I save?"
- "What is my balance?"

The assistant currently uses deterministic backend rules.

> No external LLM or AI provider is connected in Version 3.

The architecture includes an `AssistantGateway` abstraction so the current implementation can later be replaced with an external AI provider without changing the presentation layer.

## Getting Started

### Requirements

You will need:

- JDK 17 or later
- A modern web browser
- Internet access during the first Maven run
- Node.js only if running frontend tests

Check your Java installation:

```bash
java -version
```

The Maven Wrapper is included, so Maven does not need to be installed separately.

---

## Run on macOS or Linux

Clone the repository:

```bash
git clone YOUR_REPOSITORY_URL
cd hikyu-bank
```

Make the startup scripts executable:

```bash
chmod +x start.sh backend/mvnw
```

Start Hikyu:

```bash
./start.sh
```

Wait for Spring Boot to report that `HikyuBankApplication` has started.

Then open:

```text
http://localhost:8080/login.html
```

You can also start the backend directly:

```bash
cd backend
./mvnw spring-boot:run
```

---

## Run on Windows

From PowerShell or Command Prompt:

```powershell
.\start.cmd
```

Or start Spring Boot directly:

```powershell
cd backend
.\mvnw.cmd spring-boot:run
```

Then open:

```text
http://localhost:8080/login.html
```

---

## Important: Do Not Use Live Server

Version 3 is no longer a standalone static frontend.

Opening the frontend directly through VS Code Live Server, for example:

```text
http://127.0.0.1:5500/frontend/login.html
```

will not provide the required `/api/v1` backend endpoints.

This can result in errors such as:

```text
Request failed (405)
```

Run the project through Spring Boot and access the frontend through:

```text
http://localhost:8080
```

Spring Boot serves both the frontend and REST API from the same origin.

## REST API

The backend exposes its API under:

```text
/api/v1
```

### Main endpoints

| Method | Endpoint | Purpose |
| --- | --- | --- |
| GET | `/api/v1/health` | Application health |
| POST | `/api/v1/auth/login` | Start authentication |
| POST | `/api/v1/auth/code` | Generate verification code |
| POST | `/api/v1/auth/verify` | Complete verification |
| GET | `/api/v1/auth/session` | Retrieve active session |
| POST | `/api/v1/auth/logout` | End session |
| GET | `/api/v1/accounts` | List accounts |
| GET | `/api/v1/accounts/products` | Available account products |
| POST | `/api/v1/accounts` | Open/apply for an account |
| GET | `/api/v1/transactions` | Retrieve transactions |
| GET | `/api/v1/alerts` | Retrieve alert rules |
| POST | `/api/v1/alerts` | Create an alert |
| GET | `/api/v1/notifications` | Retrieve notifications |
| POST | `/api/v1/notifications/test` | Generate a demo notification |

## Storage

Version 3 currently uses an in-memory storage implementation.

Synthetic seed records are loaded from:

```text
backend/src/main/resources/seed/demo-data.json
```

Application changes remain available while the Spring Boot process is running.

Restarting the application resets the data.

There is currently:

- No SQL database
- No NoSQL database
- No JDBC connection
- No JPA persistence
- No durable account storage

The data-access layer uses repository interfaces so a persistent database implementation can be introduced later without requiring major changes to the application services or frontend.

## Security Model

Hikyu is a demonstration application and should not be treated as a production banking system.

The current architecture includes:

- Backend credential validation
- Password/PIN hashing
- Verification challenge expiry
- Attempt limits
- Session-based authentication
- Request validation
- Server-side account rules
- Restricted API endpoints

A real production deployment would additionally require:

- HTTPS
- Production identity management
- Multi-user authorization
- Persistent session storage
- Centralized rate limiting
- Audit logging
- Secure secrets management
- Database-level integrity constraints
- Monitoring and observability
- Real email/SMS providers
- Regulatory and security review

---

## Current Limitations

Hikyu Version 3 is intentionally a local demonstration.

Current limitations include:

- In-memory storage resets when the backend restarts
- Only one synthetic demo user is supported
- Sessions are local to one server instance
- Verification codes are displayed in the demo UI
- No real email or SMS provider is connected
- No real financial institution is connected
- Alert delivery is simulated
- No background alert scheduler is currently running
- The assistant is rule-based rather than powered by an external AI model
- No production-grade cloud deployment is currently configured

## AI, LCNC and Integration Direction

The current implementation uses traditional frontend development and a Spring Boot backend while keeping integration boundaries open for future tools.

Used for UI prototyping, responsive design exploration, and accessibility-focused interface refinement.

- Savings reminders
- Bill reminders
